# アプリのセキュリティチェック

このプロジェクト（Streamlit + Gemini API の個人用ライティングツール）全体を点検し、重要度つきのレポートを会話に出す。

## このスキルの前提

- **コードは変更しない。** ユーザーはレポートを読んで、直すかどうか・どう直すかを自分で決めたい。修正案はレポートの中にコードとして示すだけにする。修正を頼まれたら、そのとき改めて作業する。
- **外部に何かを送る操作（pip-audit、pip install）は、送る中身と理由を説明して許可を取ってから。** ユーザーのグローバル設定で、外部への送信には理由の説明と許可が必須とされている。
- **このアプリの実際の使われ方に合わせて重要度を決める。** ローカルで1人が使うツールに公開 Web サービス向けのチェックリストをそのまま当てると、「認証なし＝重大」のような的外れな指摘だらけになり、本当に危ない1件が埋もれる。「誰が・何をすると・何が起きるか」を書けない指摘は、指摘にしない。

## 手順

### 1. 事実を集める（読み取り専用・外部通信なし）

プロジェクト直下で実行する:

```bash
python .claude/skills/app-security-audit/scripts/collect_facts.py
```

Streamlit の実効設定、秘密ファイルの ignore 状況、秘密情報らしき文字列（伏せ字）、危険な書き方の候補、requirements と実インストール版のズレを一度に出す。Windows では、ファイアウォールの python / streamlit 向けルール、いま接続中のネットワークの種類（パブリック／プライベート）、ポートの待ち受け状況も PowerShell で読み取る（数十秒かかることがある）。出力はスクリプト自身が UTF-8 にするので `PYTHONIOENCODING` は付けなくてよい。

出力は**手がかり**であって指摘ではない。たとえば `st.markdown(` のヒットは、そこに外部由来の内容が流れるときだけ問題になる。必ず該当コードを読んで確かめる。

Streamlit の既定値を確かめたいときは `streamlit config show` が使えるが、**出力には `cookieSecret` の実値が含まれる**。全文を表示せず、必要なキーだけ grep で抜き出すこと。

### 2. データの流れを追ってコードを読む

プロジェクトの CLAUDE.md にアーキテクチャがある（`app.py` → `tools/*.py` → `core/ui.py` → `core/gemini.py`）。これに沿って、外部由来のデータがどこから入り、どこへ出るかを追う:

- **入口**: `st.text_area` / `st.text_input` / `st.chat_input` / `st.file_uploader`（`core/ui.py` の `long_text_input`）
- **通過**: 各 `tools/*.py` のプロンプト組み立て → Gemini
- **出口**: `st.write_stream` / `st.markdown` での描画、`history/history.json` への保存、履歴画面での再描画・ダウンロード
- **秘密情報**: APIキーの解決（`core/config.py` の `get_api_key`）と、それが使われる・表示され得る場所

観点ごとの確認項目と重要度の目安は `references/checklist.md` にある。**レポートを書く前に必ず読む。** 全ツールは `app.py` の `TOOLS` に並んでいるので、後から追加されたツールも漏らさず同じ観点で見る。

### 3. 依存パッケージの既知脆弱性（許可を取ってから）

1. 手順1の出力で pip-audit の有無を確認する。
2. ユーザーに次を説明して、実行してよいか確認する:
   - **送る先**: PyPI の脆弱性情報（pip-audit の既定の照会先）
   - **送る中身**: requirements.txt に書かれたパッケージの**名前とインストール済みバージョンだけ**。コード・APIキー・履歴は送らない
   - **理由**: 公開済みの脆弱性が、いま入っている版に該当するかを調べるため
   - pip-audit が未インストールなら、`pip install pip-audit` で PyPI からダウンロードし、環境にパッケージが増えることも合わせて確認する
3. 許可が出たら、インストール済みの版で固定したリストを作り、それだけを照会する（パスはスクラッチパッドなど一時的な場所にする）:

   ```bash
   python .claude/skills/app-security-audit/scripts/collect_facts.py --write-pinned <一時フォルダ>/pinned-requirements.txt
   pip-audit -r <一時フォルダ>/pinned-requirements.txt --no-deps --disable-pip
   ```

   `requirements.txt` をそのまま渡すと、`>=` 指定のため「いま入っている版」ではなく最新版を解決して調べてしまい、結果が実態とずれる。固定リストを使うのはそのため。古い pip-audit で `--disable-pip` が無いと言われたら外す。
4. この方法は requirements.txt に直接書かれたパッケージだけを調べ、その依存先（間接依存）は調べない。レポートの「今回確認していないこと」に書く。
5. 断られた、または確認が取れない状況なら実行せず、レポートに「依存パッケージの脆弱性照会は未実施」と書く。

### 4. 重要度を決める

| 重要度 | 目安 |
|---|---|
| 重大 | いまこの瞬間、他人が APIキーを入手できる／他人の操作で任意のコードが動く |
| 高 | 条件が1つ揃えば上記に至る。または秘密情報・個人データが第三者に渡る |
| 中 | 悪用に複数の条件が要る。または被害が限定的（出力の誘導、課金の浪費、内部情報の露出） |
| 低 | 多層防御の不足。単独では実害に結びつきにくい |

迷ったら次の3つを書き出す。書けなければ1段下げるか、指摘から外して「問題がないことを確認した項目」に回す:

- **誰が**（同じ Wi-Fi の他人／公開リポジトリの閲覧者／読み込ませた文書の作者／この PC を触れる人）
- **何をすると**（具体的な操作）
- **何が起きるか**（キーの悪用、データの持ち出し、履歴の消去 など）

条件が組み合わさって重くなるものは、組み合わせで評価する。例: 「LAN から届く」×「認証なし」×「`.env` にキー」×「履歴画面で全履歴を読める・書き出せる・消せる」。

逆に、**同じ根本原因から派生するものは1つの指摘にまとめ、重要度を二重に数えない**。例: LAN に公開されているせいでエラーの詳細も他人に見える場合、エラー詳細の項目は低のままにして、LAN 公開の指摘の中で「これを直せばエラー詳細の露出も消える」と触れる。読み手が「直すべきことは実質いくつあるか」を正しくつかめるようにするため。

### 5. レポートを出す

会話に次の形で出す。ファイルへの保存はユーザーに頼まれたときだけ（脆弱性の詳細が書かれた文書なので、置き場所はユーザーが決める）。

~~~~markdown
# セキュリティチェック報告

- 実施日: YYYY-MM-DD
- 対象: <プロジェクトのパス>
- 実施した確認: 設定とコードの静的確認 ／ 依存パッケージの脆弱性照会（実施 または 未実施）

## 結論
<3行以内。いちばん先に手を打つべきことを最初に書く>

## 指摘一覧
| # | 重要度 | 内容 | 場所 |
|---|---|---|---|
| 1 | 高 | ... | `path:line` |

## 詳細

### 1. [高] <タイトル>
- **場所**: `path:line`
- **起き得ること**: 誰が・何をすると・何が起きるか
- **根拠**: 実際に確認したコード／設定値／コマンド出力の短い引用
- **修正案**:
  ```toml
  ...
  ```

## 問題がないことを確認した項目
- <項目>: <どう確かめたか>

## 今回確認していないこと
- <例: 間接依存パッケージの脆弱性、別の端末から実際に接続できるかの確認>
~~~~

書き方:

- 指摘は重要度の高い順に並べる。
- 場所は `ファイル:行` で書く（エディタでクリックして飛べる）。
- 根拠には、実際に読んだコード・設定値・コマンド出力を短く引用する。推測で書かない。
- 修正案は、そのまま貼れる程度に具体的なコードや設定で示す（適用はしない）。
- ユーザーはプログラミングを学習中。専門用語（XSRF、プロンプトインジェクション、SSRF など）は初出で一言説明する。
- 「問題がないことを確認した項目」も省かない。何を見て安全と判断したかが分かると、次にコードを変えたとき何を守ればいいかが伝わる。
